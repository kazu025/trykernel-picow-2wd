# TryKernel 2WD Heartbeat通信監視機能 設計書

## 1. 概要

### 1.1 目的

Raspberry Pi Pico上で動作するTryKernel 2WDに、Heartbeat（生存確認）による通信監視機能を追加する。

PCから定期的にHeartbeatを送信し、一定時間受信できなかった場合にモータを自動停止させる。

本機能は、RTOSにおける周期処理、タスク間通信、排他制御、タイムアウト処理、フェイルセーフ設計を学習することを目的とする。

### 1.2 開発方針

開発は以下の2段階で進める。

**Phase 1：Raspberry Pi Pico**

- UARTを使用してHeartbeatを受信する。
- 50ms周期で通信状態を監視する。
- 通信タイムアウト時にモータを停止する。
- Linux MintまたはWindowsからHeartbeatを送信して検証する。

**Phase 2：Raspberry Pi Pico W**

- Wi-FiによるTCP/IP通信を追加する。
- PCのWebブラウザからロボットを操作する。
- HTTPまたはWebSocketでHeartbeatを受信する。
- 通信切断時の自動停止機能を実装する。

Phase 1で開発した通信監視ロジックは、Phase 2でも再利用する。

## 3. 機能仕様

### 3.1 Heartbeat通信仕様

| 項目 | 設定値 |
|---|---|
| Heartbeatコマンド | `hb` |
| 通信方式 | UART |
| PC送信周期 | 100ms |
| 通信監視周期 | 50ms |
| タイムアウト | 500ms |
| 起動時の状態 | DISCONNECTED |
| タイムアウト時 | モータ即時停止 |
| 通信復旧後 | 自動走行再開は禁止 |
| 停止コマンド | 通信状態に関係なく実行可能 |

Heartbeatは既存のUARTコマンド処理機構を使用する。

```text
hb\r\n
```

受信時に正常なコマンドとして解析し、通信監視モジュールに通知する。

通常のHeartbeat受信に対してはUARTログを出力せず、接続や切断などの状態変化時のみログを出力する。

### 3.2 通信状態

通信状態は次の3種類とする。

| 状態 | 説明 | モータ操作 |
|---|---|---|
| DISCONNECTED | 起動直後、Heartbeat未受信 | 禁止 |
| CONNECTED | 正常なHeartbeatを継続受信 | 許可 |
| TIMEOUT | Heartbeatの受信が規定時間途絶えた | 禁止・即時停止 |

状態遷移：

```text
        システム起動
             |
             v
      +--------------+
      | DISCONNECTED |
      +--------------+
             |
       有効なhb受信
             |
             v
       +-----------+
       | CONNECTED |
       +-----------+
             |
      Heartbeat 500ms
         タイムアウト
             |
             v
       +-----------+
       |  TIMEOUT  |
       +-----------+
             |
        モータ即時停止
             |
        新しいhb受信
             |
             v
       +-----------+
       | CONNECTED |
       +-----------+
             |
      新しい走行コマンド
        を受信して操作
```

TIMEOUTからCONNECTEDへの復帰時には、以前の走行コマンドを再利用しない。

また、CONNECTED状態であっても、障害物検出など他の停止条件が成立している場合には走行を許可しない。

## 4. ソフトウェア構成

### 4.1 システム構成

```text
             PC
              |
              | UART
              | "hb" (100ms周期)
              v
    +--------------------+
    | task_uartrx        |
    | UART受信タスク     |
    | Priority = 4       |
    +--------------------+
              |
              v
    +--------------------+
    | command_execute()  |
    | UARTコマンド解析   |
    +--------------------+
              |
              v
    +--------------------+
    | heartbeat.c        |
    | Heartbeat状態管理  |
    +--------------------+
              ^
              |
    +--------------------+
    | Heartbeat監視      |
    | 50ms周期           |
    | Priority = 5（案） |
    +--------------------+
              |
        通信タイムアウト
              |
              v
    +--------------------+
    | モータ走行禁止     |
    | 停止要求           |
    +--------------------+
              |
              v
    +--------------------+
    | task_motor_stop_   |
    | drive()            |
    +--------------------+
              |
              v
         PWM出力停止
```

Heartbeat監視タスクは、UART受信タスクおよびモータ制御タスクとは独立して動作する。

### 4.2 タスク構成

既存タスクと追加予定タスクは次のとおり。

| タスク | 優先度 | 周期・起動条件 |
|---|---:|---|
| UART受信 | 4 | UART受信イベント |
| Heartbeat監視（新規） | 5（案） | 50ms |
| UART送信 | 6 | UART送信イベント |
| モータ制御 | 8 | 50ms |
| 距離測定 | 10 | 既存実装に従う |
| LED制御 | 12 | 既存実装に従う |

Heartbeat監視タスクのスタックサイズは、初期値として1024バイトを想定する。

実機デバッグ時にスタック使用量を確認し、必要に応じて調整する。

### 5.2 heartbeat.h

Heartbeat監視機能の公開インターフェースを定義する。

主要API案：

```c
typedef enum {
    HEARTBEAT_DISCONNECTED,
    HEARTBEAT_CONNECTED,
    HEARTBEAT_TIMEOUT
} HEARTBEAT_STATE;

ER heartbeat_init(void);

void heartbeat_received(void);

BOOL heartbeat_is_connected(void);

void task_heartbeat(INT stacd, void *exinf);
```

各APIの役割：

| API | 役割 |
|---|---|
| `heartbeat_init()` | Heartbeat監視機能の初期化 |
| `heartbeat_received()` | 正常なHeartbeatの受信を通知 |
| `heartbeat_is_connected()` | 現在の通信状態を取得 |
| `task_heartbeat()` | タイムアウト監視タスク |

必要に応じて、状態取得APIや走行許可確認APIを追加する。

### 5.3 heartbeat.c

Heartbeat通信状態を管理する。

内部管理情報の例：

```c
static HEARTBEAT_STATE heartbeat_state;
static UW heartbeat_elapsed_ticks;
```

- `heartbeat_state`：現在の通信状態
- `heartbeat_elapsed_ticks`：最後の正常受信以降の監視周期数

実装時には、監視周期の位相によって500msより早くタイムアウト判定されないようにする。

そのため、可能であればTryKernelの単調増加するシステム時刻を使い、最後の正常受信時刻との差分で判定する方式を優先する。

周期カウンタ方式を採用する場合は、初回周期の位相差を考慮して、実際のタイムアウト時間を検証する。

### 5.4 command.c

コマンドテーブルに次のエントリを追加する。

```c
{"hb", cmd_heartbeat, "receive heartbeat from PC"},
```

Heartbeatコマンドを処理する関数を追加する。

```c
static void cmd_heartbeat(int argc, char *argv[]);
```

有効なコマンドを受信した場合は `heartbeat_received()` を呼び出す。

通常のUARTコマンドを受信しただけではHeartbeatの監視時間を更新しない。

Heartbeatが正常でない場合、走行開始コマンドの実行を禁止する。

対象となるコマンド：

- `motor`：左右モータの個別操作
- `drive`：前進・後退・左右旋回
- `f/b/r/l`：短縮走行コマンド

`v` コマンドは速度設定のみなのでモータを動かさないが、設定したデューティ比で走行開始する際にはHeartbeat状態を確認する。

`motor stop`、`drive stop`、`s` などの停止操作は常に許可する。

### 5.5 task_motor.c

通信監視がタイムアウトした場合、既存の以下の関数を利用する。

```c
task_motor_stop_drive();
```

この関数は、時間指定走行と障害物回避制御の状態を解除し、`motor_stop_all()` によってモータ出力を即時停止する。

Heartbeat監視タスクから停止処理を要求する。

停止後には、古い走行目標や障害物回避シーケンスによってモータが再始動しないようにする。

なお、コマンド実行時の通信状態確認だけでなく、モータ側にも走行許可条件を設ける。これは通信監視とモータ制御の競合を防ぐためである。

走行禁止状態の設定と走行目標の更新は、既存のDI/EIによる排他制御と整合する形で実装する。

## 6. タイムアウト処理

### 6.1 時間計算

Heartbeat受信周期：

\[
T_{HB}=100\text{ ms}
\]

通信監視周期：

\[
T_{MON}=50\text{ ms}
\]

タイムアウト時間：

\[
T_{TIMEOUT}=500\text{ ms}
\]

単純な周期数換算では、

\[
N=\frac{T_{TIMEOUT}}{T_{MON}}
=\frac{500}{50}=10
\]

となる。

ただし、この10周期は監視周期とHeartbeat受信タイミングが一致している場合の値であり、実際には位相差がある。

そのため、最後のHeartbeat受信からの経過時間が500ms以上になったことを確認してから停止要求を発生させる。

監視周期50msに加えて、タスクのスケジューリング遅延と停止処理時間も発生するため、停止までの総時間を実機で測定する。

### 6.2 タイムアウト時の動作

```text
Heartbeat受信
      |
      v
最終受信時刻を更新
      |
      v
50ms周期監視
      |
      +-- 500ms未満
      |       |
      |       +-- 通信正常を維持
      |
      +-- 500ms以上
              |
              v
        TIMEOUTへ遷移
              |
              v
        走行禁止状態に設定
              |
              v
        時間指定走行を解除
              |
              v
        自動障害物回避を解除
              |
              v
        モータ即時停止
```

停止要求はタイムアウトへ遷移した際に発生させる。

通信が復旧するまで、走行禁止状態を保持する。

## 7. 安全設計

### 7.1 通信断時の停止

Heartbeatが規定時間受信できない場合は、モータを即時停止する。

通常のランプ減速ではなく、既存の `motor_stop_all()` を使う停止経路とする。

### 7.2 自動再始動の防止

通信が復旧しても、過去の走行コマンドでは再始動しない。

再始動には、復旧後に新しい走行コマンドを受信する必要がある。

### 7.3 障害物検出との連携

既存のAE-VL53Lによる距離測定機能を維持する。

現在の仕様では、20cm以内で前進を禁止し、後退・旋回は許可する。

ただし、通信断による停止は前進・後退・旋回のすべてに優先する。

### 7.4 排他制御

Heartbeat状態はUART受信タスクとHeartbeat監視タスクから参照・更新される。

そのため、状態の更新とタイムアウト判定には排他制御が必要となる。

RP2040のシングルコア構成では、既存のPRIMASKによる `DI()` / `EI()` を使用できる。

ただし、割り込み禁止区間はできるだけ短くし、UART出力や長時間の処理を含めない。

### 7.5 本機能の制約

Heartbeat監視は学習用のソフトウェア安全対策であり、機能安全規格への適合や完全な安全停止を保証するものではない。

監視タスクやカーネルそのものが停止した場合は、Heartbeat監視だけでは異常を検出できない。

将来的にはハードウェアウォッチドッグ、モータドライバの出力禁止機能なども検討する。

### 8.2 Pico実機テスト

PCからUARTでHeartbeatを送信する。

```text
PC                      Pico
 |                        |
 |------ hb ------------->|
 |                        |
 |------ hb ------------->|
 |                        |
 |------ hb ------------->|
 |                        |
 |   送信停止             |
 |                        |
 |                   500ms経過
 |                        |

```

実機では以下を確認する。

1. Heartbeat正常時に走行できる。
2. Heartbeat送信を停止するとモータが停止する。
3. 停止後に勝手に再始動しない。
4. Heartbeatを再開すると通信状態が回復する。
5. 新しい走行コマンドで再び操作できる。
6. 障害物20cm停止機能が従来どおり動作する。

## 12. まとめ

今回のHeartbeat通信監視機能は、TryKernel 2WDに通信断時の自動停止を追加するものである。

学習上の重要なポイントは以下のとおり。

1. 周期ハンドラとセマフォによる周期監視
2. UARTタスクと監視タスク間の状態共有
3. タイムアウト処理
4. DI/EIによる排他制御
5. 状態遷移による通信管理
6. 通信断時のフェイルセーフ停止
7. 通信復旧後の自動再始動防止

まずPicoのUARTで動作を完成させ、その後Pico WによるWebブラウザ操作へ拡張する。

この構成により、通信方式とモータ制御を分離した再利用性の高いシステムを目指す。
